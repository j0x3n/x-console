# B28 进程合并、终端里跑脚本、容器排序和日志过滤

用户要求（2026-09-28）：

- 进程标签里很多重名进程，加一个“合并”勾选框，默认勾上。
- 终端里加一个面板，列出和这台机器关联的监控脚本，可以一键运行。
- 容器可以按 CPU、内存排序。镜像默认展开，并且可以删除。日志可以按类型过滤。

## 前端（已完成，提交 B28）

- **进程合并**（`servers/components/ProcessesTab.tsx`）：“合并同名进程”勾选框，默认勾上，存在 `localStorage` 的 `xc.hosts.mergeProcs`。合并时请求 1000 条（接口上限 2000，不用改后端）。一组一行，显示 `×N`、CPU 和内存之和、最早启动时间；点一行展开；“更多 → 结束这一组”逐个发 TERM，确认框写清楚个数。纯函数 `groupProcesses`。
- **终端里的脚本**（`servers/components/TerminalScripts.tsx`）：终端右边 260px 的面板，列出 `defaultHostIds` 包含这台机器的监控脚本，可以勾“显示全部”。Windows 只列 PowerShell 脚本，其他只列 bash、sh。
  - “在终端运行”：bash、sh 用加引号的 heredoc（`bash <<'XC_EOF'`，脚本里有同名结束标记时自动加下划线）；PowerShell 用 `-EncodedCommand`（UTF-16LE 的 base64）。直接写进当前终端，和键盘输入一样。
  - “后台运行”：调用已有的 `POST /scripts/{id}/run`，只选这台机器，要提升权限。
  - 脚本里有 `rm -rf`、`shutdown`、`reboot`、`mkfs`、`dd of=` 这类字样时先确认。纯函数 `terminalInput`、`isRisky` 有测试。
- **容器**（`monitoring/DockerTab.tsx`）：
  - 按名称、状态、CPU、内存排序（桌面点表头，手机用下拉）。CPU 和内存来自已有的 `/docker/stats`，不用改后端。
  - 镜像默认展开，标题可以折叠。每个镜像有“删除”，有容器在用时按钮不可点，悬停写出在用的容器。有没人用的镜像时显示“清理没用的镜像”，确认框里写能释放多少（前端按 `containers == 0` 的镜像大小求和）。
  - 日志弹窗改用公共的 `components/log/LogViewer`：按级别（关键字判断）、按输出（标准输出 / 错误输出）、按关键字过滤并高亮，只渲染看得到的行，最多保留 5000 行，往上翻时停止自动滚动并提示“有 N 条新日志”。
  - 跟随日志的地址加了 `format=json`。旧服务端忽略这个参数、照旧发纯文本，这时没有“输出”筛选。

## 契约

`api/modules/monitoring.yaml`：

- `/hosts/{hostId}/docker/containers/{containerId}/logs/follow` 加参数 `format`（`text`、`json`）。`json` 时每个文本帧是 `DockerLogLine` 数组（`stream`、`text`、`time`）。
- 新增 `DELETE /hosts/{hostId}/docker/images/{imageId}`、`POST /hosts/{hostId}/docker/images/prune`。现在由 `modules/monitoring/pending.go` 回 501。

## 后端（待做，给开发者）

### 1. 日志带上输出来源

- 代理的 `docker` 包（`internal/agent/docker/docker.go` 的日志部分）已经会解析 Docker 多路复用流的 8 字节帧头，但解析后把来源丢掉了。改成保留来源：帧头第 1 字节 1 是 stdout、2 是 stderr。
- TTY 容器（`Config.Tty = true`）没有多路复用，全部当 stdout。
- 请求 Docker API 时加 `timestamps=1`，每行开头是 RFC3339Nano 时间，拆出来放进 `time`。
- 协议：代理那边的流事件加 `stream` 字段；服务端 `format=json` 时每 100 毫秒或每 200 行把攒下的行打包成一个 JSON 数组发一帧；`format=text` 或不传时保持现在的纯文本（旧前端还在用）。
- 单行超过 16 KB 截断，末尾加 `…`。

### 2. 删除镜像

- 代理加方法 `docker.image_remove {id}`：调用 Docker API `DELETE /images/{id}`（不带 `force`）。Docker 回 409 时把消息原样带回。
- 服务端 `RemoveImage`：`auth.RequireElevated`；`imageId` 只允许 `[a-zA-Z0-9:._/@-]`；代理回 409 时服务端也回 409，消息写“有容器在用这个镜像：<容器名>”（先调一次容器列表找出在用的容器名）。审计 `docker.image_remove`。成功后发 `docker.image_removed` 事件（前端已对 `docker.` 前缀刷新）。

### 3. 清理镜像

- 代理加方法 `docker.image_prune`：调用 `POST /images/prune?filters={"dangling":["false"]}`（等同 `docker image prune -a`），返回 `ImagesDeleted` 的个数和 `SpaceReclaimed`。
- 服务端 `PruneImages`：`auth.RequireElevated`，审计 `docker.image_prune`，发 `docker.images_pruned` 事件，回 `{deleted, spaceReclaimed}`。
- 更新 `docs/04-agent-protocol.md` 的方法列表。

### 4. 测试

- 代理：用一段手工拼的多路复用字节流测试解析（stdout、stderr 交替，一帧跨两次读取，带时间戳）。
- 服务端：假代理回 409 时接口回 409 且带容器名；没提升权限回 403。
- `format=json` 的打包：200 行以内攒一帧，超过分帧。

## 验收

- 一台跑了 30 个 `php-fpm` 的机器，合并后只有一行 `php-fpm ×30`，CPU 和内存是总和；取消勾选后是 30 行。
- 终端面板里点“在终端运行”，多行 bash 脚本（含 `$`、引号、反引号）原样执行，输出和直接跑一致。
- 按内存排序后第一行内存最大。删除一个没被使用的镜像成功；被使用的镜像按钮不可点；清理后提示释放了多少。
- 日志选“错误输出”只显示 stderr 的行；选“只看错误”只显示含错误关键字的行；搜索的词高亮。
- 代理改动带单元测试，Windows 交叉编译和 vet 通过。
