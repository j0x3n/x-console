# B216 用服务器上的浏览器读 iCloud 备忘录和提醒事项

用户 2026-10-15 提出。Apple 备忘录和提醒事项没有给第三方用的接口（不走 CalDAV，也没有网页接口）。用户的做法是：用 B205 的服务器浏览器登录 icloud.com，定时读里面的数据；页面改版读不到时，自动调用 agent 修。

## 先说清楚的几件事

- **还不知道能不能行，第一步先试。** 下面几件事没有用真实账号验证过，可能直接卡住：
  - 从国外机房的 IP 用无头浏览器登录 Apple ID，可能被要求反复验证，或者被拒绝。
  - Apple ID 的双重认证要在你的苹果设备上点“允许”，再输 6 位码。浏览器保存的登录多久失效，没有公开说明。
  - 开了“高级数据保护”的账号，网页版默认看不到备忘录。要在 iPhone 的 设置 → Apple ID → iCloud 里打开“通过网页访问 iCloud 数据”。
  - icloud.com 的备忘录页面是怎么组织的（同源 iframe 还是别的），网页内部调的接口返回什么格式，都要实际打开看。
- **只读，不写回。** 备忘录和提醒事项只从 iCloud 读到 X Console。写回要在网页上模拟编辑，改版时容易把内容写坏，坏了没法恢复。在 X Console 里改了 iCloud 来的笔记，下次同步会被 iCloud 的内容覆盖，所以这些笔记在 X Console 里只读。
- **Apple ID 密码不存。** 登录由用户在接管页面（B205、B206）上自己完成，服务器只加密保存登录后的 Cookie。登录过期时通知用户再登录一次。
- **自动修复分两层，代码不自动上线。** 详见下面“读不到时怎么修”。
- **费用。** 平时按“读法”读，不调 AI。只有读不到时才调 AI，一次修复大约几到几十万 token。

## 第一步：探路（先做这个）

在开发其他部分之前做，花的时间少：

1. 用现有的“网站自动化”接管页面（B206 的“打开浏览器”）打开 `https://www.icloud.com`，用户自己登录，完成双重认证，保存登录状态。
2. 记下：登录要几步、有没有被拦、备忘录和提醒事项页面能不能打开、页面结构（iframe、列表、正文）、网页加载数据时调的接口和返回格式。
3. 过 1 天、3 天、7 天各检查一次登录还在不在。
4. 结果写进 `docs/qa/B216-探路.md`，再决定下面的“读法”用哪种。

如果登录被拦或者几小时就掉，这个任务就停下来，告诉用户结论，不往下做。

## 要什么

- 新模块 `icloud`，页面放在 设置 → 账号 下的“iCloud 网页同步”。
- 显示：登录状态、上次同步时间、读到多少条备忘录和提醒、最近的错误、“重新登录”“立即同步”按钮。
- 备忘录：同步到笔记里一个单独的文件夹“iCloud 备忘录”，保留 iCloud 上的文件夹结构（作为标签）。只读，界面上有“来自 iCloud，只读”的标记。
  - 第一版只同步文字、清单（转成 Markdown 的 `- [ ]`）和表格（转成 Markdown 表格）。图片、附件、手绘先不同步，在笔记里写一行“这里有一张图片，没有同步”。
  - 加了锁的备忘录读不到，跳过。
  - iCloud 上删掉的备忘录，X Console 里也删掉（移到回收站）。
- 提醒事项：同步到提醒页，作为一个外部来源（B37 的 `reminders.sources`），显示标题、到期时间、所属列表、是否完成。只读，不在 X Console 里推送，以免和 iPhone 上的提醒重复弹出。
- 间隔默认 30 分钟，最短 15 分钟。只打开有变化的备忘录（按列表里的修改时间判断）。

## 读法

探路之后二选一，优先第一种：

1. **读网页加载的数据。** 浏览器里记录 icloud.com 调接口拿到的返回，从里面取备忘录和提醒。页面改版通常不改这些接口，比读页面稳定。B205 的浏览器包要加“读取指定网址的返回内容”。
2. **读页面。** 用一份“读法”记录列表、标题、正文、修改时间在页面上的位置。“读法”存在数据库里，不写在代码里，所以修它不用改代码。

## 读不到时怎么修

怎么算“读不到”：报错；或者读到的条数比上次少了一半以上；或者读到的标题和上次几乎都对不上。这时本次同步作废，不改 X Console 里已有的数据。

1. **重试一次。** 排除网络问题。
2. **AI 修读法。** 把当前页面的结构交给 AI（用 设置 → AI 里的 Agent 模型，或网站自动化里选的模型），让它重新找到列表、标题、正文的位置，或者重新找到数据接口，生成新的读法。
   - 发给 AI 之前，把备忘录正文换成占位文字，只留结构和标题，避免把私人内容交给模型，也避免正文里的文字影响 AI 的判断。
   - 新读法读出来的条数和标题要和上次大体一致，才算修好，自动换上。否则算没修好。
   - 一天最多修 3 次。
3. **AI 修代码。** 第 2 步也不行，说明要改代码（比如接口格式变了）。这时：
   - 自动建一个 Agent 编码任务（`contracts.Coding`），把错误、页面结构（同样去掉正文）、相关代码位置交给它。
   - Agent 在单独的分支上改，跑这个模块的测试，开 PR，然后通知用户。
   - **不自动合并，不自动部署。** 用户看过 PR 后合并、部署。原因：AI 改的代码要跑在你的服务器上，还能拿到你的 iCloud 登录状态。如果页面内容影响了 AI，让它写进了别的东西，自动上线就没有人拦得住。
   - 同一个问题只建一个任务，任务没处理完不再建新的。
4. 同步状态标成“出错”，页面上显示卡在哪一步和修复进度。

## 安全

- iCloud 的 Cookie 和本地存储用 `secrets.Box` 加密存。查看和重新登录要 `auth.RequireElevated`。
- 浏览器只允许访问 `icloud.com`、`apple.com`、`icloud-content.com` 及其子域名。
- 这个任务的浏览器会话不做任何点击写操作。按钮文字检查沿用 B206 的危险字样。
- AI 的请求和日志里不出现备忘录正文和 Cookie。测试里要检查。

## 验收

- 探路的结果写进 `docs/qa/B216-探路.md`，用户看过后再开始下面的开发。
- 用本地假网站（模仿探路记下的结构）测：首次同步、增删改、条数骤减时不覆盖、读法失效后 AI（假模型）修好、修不好时建编码任务（假的 `contracts.Coding`）、登录过期通知。
- 正文不出现在发给模型的请求里。
- 端到端补一条：假网站同步后笔记里出现“iCloud 备忘录”文件夹，内容只读。
