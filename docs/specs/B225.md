# B225 验证码马上推，营销不推，Jev 没把握就改用对话模型

2026-10-15 用户说：再判断验证码类邮件并且通知，过滤营销邮件不通知，Jev 置信度低于等于 85% 就调用原来的对话模型。

## 要什么

1. 分拣多一个标记：这封是不是验证码、一次性密码或登录码。它不是新类别。验证码邮件仍是通知。要处理的邮件如果里面也有验证码，类别仍是要处理，标记也保留。
2. 新邮件里，验证码马上推送，标题前面加“（验证码）”。要处理的仍马上推送。普通通知仍等合并推送。
3. 营销邮件不推送。一次来了多封时，营销的不写进那一条合并通知。剩下的没有了就不发。剩下的里面有要处理或验证码，这条合并通知马上发。
4. 没分拣出来的邮件照旧推送。分拣关着，或者模型没给出结果，都不当成营销丢掉。
5. 选了 Jev 时，类别这一题的置信度低于或等于 0.85，这封不算 Jev 分完，改走原来的整封分拣。高于 0.85 的仍用 Jev。同一批里可以一部分用 Jev，一部分改走对话模型。整批都没把握时，整批改走对话模型，不把这次当成 Jev 故障。
6. 对话模型也要判断验证码。营销一律不是验证码。

## 怎么做

- `mail_triage` 加 `code`，只加不删。类别的取值不变。
- Jev 多问一题：是不是要抄的验证码。通知的说明里不再把验证码当成“不用看”的例子，避免每封通知都被当成验证码。
- 置信度看类别那一题返回的 `confidence`。没带这个字段时按 0 处理，改走对话模型。调用已经成功的，用量照记。

## 验收

- 主题里带验证码的新邮件马上推送，标题以“（验证码）”开头，今日待办里不出现（它不是要处理）。
- 营销邮件不产生通知。列表里仍能按营销筛到。
- 普通通知仍等合并推送。要处理的仍马上推送。
- Jev 置信度 0.85 的那封不采用，对话模型会再分一次。置信度更高的仍采用 Jev 的结果。
- 没有连真实 TypeSafe，也没有真实验证码邮件。
