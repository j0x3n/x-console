# B127 通知合并推送

来源：[B127-B139 建议](B127-B139-建议.md) 第 7 条。

## 要什么

除了紧急通知，其余通知先攒着，每天固定几个时间点合并成一条推送。默认 11:00、15:00、19:00，按服务端时区，可以改。紧急的立即发。每一类通知可以单独选“立即”或“合并”。

## 现状

- 所有模块都调用 `Notify.Send`（或 `SaveTx` 加 `Dispatch`）。最后都走 `Service.Dispatch`：先写进通知中心并发 `notification.created` 事件，再按路由发到外部渠道（浏览器推送、Telegram、Bark、Server 酱）。
- 外部渠道由 `reminders` 模块注册。路由规则和免打扰时段也在那里。免打扰时段内，除了紧急（`urgent`）的，其余不发外部渠道，也不会补发。
- Telegram 和浏览器推送支持按钮（`Notification.Actions`），例如提醒的“完成/稍后”。

## 默认做法（我自己选的）

1. **总开关默认关。** 打开前行为和现在完全一样。用户在设置里打开后才生效。
2. **通知中心照旧立即写入。** 只延迟外部渠道（浏览器推送、Telegram、Bark、Server 酱）。用户打开面板时随时能看到全部通知。
3. **带按钮的通知一律立即发，不合并。** 合并消息里放不下每条自己的按钮，丢了按钮会让“完成/稍后”失效。所以只要 `Actions` 不为空，不管分类怎么设都立即发。提醒、习惯提醒、番茄钟结束、Agent 等你决定都带按钮，所以实际上都是立即的。
4. **紧急一律立即：** `Priority` 是 `urgent` 的通知，和 `Notification.Immediate` 为真的通知。`Immediate` 是新加的可选字段，默认 `false`，现有调用方不用改。
5. **分类按 `Kind` 匹配，第一个匹配的生效。** 没有匹配的归“其他”。“其他”里优先级是 `high` 的也立即发，避免高优先级的未知通知被拖到几小时后。
6. **免打扰时段内不发合并。** 到点时在免打扰里，就等免打扰结束，结束后的下一次检查（一分钟内）发出。跨过好几个时间点也只发一条。
7. **积压太旧的不丢。** 超过 36 小时的条目照常发出，在条目后标出原来的时间。
8. **队列条数上限 1000。** 超过时丢最旧的。这是防止某个来源刷屏把数据库撑大，正常使用碰不到。
9. **渠道全部失败时保留队列。** 10 分钟后重试。没有配置任何渠道时，到点会清空队列（通知中心里仍有）。
10. **关掉总开关时，积压在一分钟内发出。** 调度器每分钟检查一次，开关关着又有积压就发。免打扰时段内则等免打扰结束。
11. **手动“现在发送”不看时间点，但看免打扰。** 免打扰时段内按钮返回提示，不发出。
12. **合并消息按分类分组。** 分类和设置里的一样。每组最多列最近 5 条，其余写“另有 N 条”。全部最多列 25 条。有公网地址时每条带链接。

## 分类和默认值

| id | 匹配的 Kind | 默认 | 说明 |
| --- | --- | --- | --- |
| `alert` | `host.*` `monitor.*` `router.*` `backup.*` | 立即 | 服务器、监控、路由器、备份告警 |
| `security` | `security.*` `auth.*` `login.*` | 立即 | 安全相关（目前还没有发送方，先占位） |
| `agent_decision` | `ai_agent.decision` | 立即 | AI Agent 等你批准或回答 |
| `reminder` | `reminder.*` `habit.*` `workout.*` `focus.*` | 立即 | 提醒、习惯、训练、番茄钟，到点才有意义 |
| `brief` | `brief.*` `weather.*` | 立即 | 早报和天气，有时间性 |
| `agent_progress` | `ai_agent.*` `coding_task.*` | 合并 | Agent 和编码任务的进度 |
| `mail` | `mail.*` | 合并 | 新邮件 |
| `github` | `github.*` `repo.*` | 合并 | GitHub 动态 |
| `project` | `issue.*` `subscription.*` | 合并 | 卡片到期、订阅到期 |
| `other` | 其余所有 | 合并 | 自动化、流量提醒、AI 动作发的通知等 |

## 接口

`api/modules/reminders.yaml` 加三个操作（标签 `notify`）：

- `GET /notify/digest` 取设置和状态：`enabled`、`times`、每类的 `mode` 和 `defaultMode`、`pending`（积压条数）、`oldestAt`、`lastSentAt`、`nextAt`（下一个时间点）。
- `PUT /notify/digest` 保存设置：`enabled`、`times`（1 到 6 个不重复的 `HH:MM`）、`modes`（分类 id 到 `now` 或 `digest`）。分类 id 不认识返回 400。不需要提升权限，和免打扰、路由规则一致。
- `POST /notify/digest/flush` 现在发送积压。返回 `count`（这次合并了几条）和 `delivered`（几个渠道收到了）。队列空时 `count` 为 0。免打扰时段内返回 409 `quiet_hours`。所有渠道都失败返回 502。

设置存在 `settings` 的 `notify.digest`。发送状态存在 `notify.digest_state`。都不加密（没有令牌）。

## 数据

迁移 `20261012010000_m30_b127_notify_digest.sql`：新表 `notify_digest_queue`（`id`、`notification_id`、`created_at`、`kind`、`title`、`body`、`link`、`priority`、`source`、`category`）。存的是通知的副本，不依赖通知中心的记录，重启不丢。

## 代码位置

- `backend/internal/server/notify/notify.go`：公共路径。加 `Notification.Immediate`、`Holder` 接口和 `SetHolder`，`Dispatch` 在发外部渠道前问一次 `Holder`；加 `DeliverNow`，同步发给已路由的渠道并返回成功和失败的渠道数。没装 `Holder` 时行为不变，所有调用 `Notify.Send` 的模块自动受益，一个都不用改。
- `backend/internal/server/modules/reminders/digest.go`：分类、`Holder` 实现、时间点计算、合并内容、发送。
- `backend/internal/server/modules/reminders/digest_handlers.go`：三个接口。
- `web/src/features/reminders/DigestCard.tsx`：设置页“推送合并”卡片，放在“免打扰时段”卡片前面。

## 验收标准

1. 总开关关着时，所有通知和以前一样立即发。
2. 开着时，合并类通知不发外部渠道，通知中心里立即能看到。
3. `urgent`、`Immediate`、带按钮的通知立即发。
4. 到时间点发一条合并消息，包含各分类的标题，条数多时截断并写明还有几条。队列空时不发。
5. 每类可以改成立即或合并，保存后马上对新通知生效。
6. 免打扰时段内到点不发，免打扰结束后发一次。
7. 重启后队列还在，时间点不重复发。
8. 超过 36 小时的条目照发，标出原来的时间。
9. 设置页能改开关、时间点、每类的模式，显示积压条数，有“现在发送”按钮。
10. 手机宽度 390px 下没有横向滚动。

## 测试

后端（`modules/reminders/digest_test.go`，外部测试包，用假的 Telegram 服务）：

- 关着时立即发。
- 合并类被攒下，通知中心有记录，Telegram 没收到。
- `urgent`、`Immediate`、带按钮的立即发。
- 分类设置：把 `alert` 改成合并后被攒下，把 `mail` 改成立即后立即发。
- 时间点：没到点不发，到点发一条，同一个时间点不重复发，队列空时不发。
- 免打扰顺延：免打扰内到点不发，结束后发。
- 重启：用同一个数据库再起一个服务，队列还在，能发出。
- 合并内容：分组、标题、链接、截断、超过 36 小时的标注。
- 手动发送：返回条数，免打扰内 409，队列空返回 0。
- 校验：时间格式错、分类 id 不认识返回 400。
- 渠道全失败时队列保留。

前端（`DigestCard.test.tsx`）：显示积压条数，改模式后保存的请求内容，点“现在发送”调用接口。

## 没有验证的

- 没有连真实的 Telegram、Bark、浏览器推送，只用假服务验证了请求内容。
- 没有在真实的长时间运行里观察过调度器每分钟的检查。时间点逻辑用固定时间的单元测试覆盖。
