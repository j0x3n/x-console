# B129 AI 编码投入产出对账

对应 [B127-B139-建议.md](B127-B139-建议.md) 第 9 条。新模块 `codingroi`，迁移 `20261012030000_m32_b129_codingroi.sql`。

## 要什么

每个编码任务花了多少，有没有产出。按周（也可按月）、按仓库、按工具或 Agent 出一张对账表，让用户用自己的数据判断哪类任务交给 AI 划算。

页面上只写一句说明：AI 划不划算只能看你自己的数据，别人的研究结果因人而异。研究来源只写在这份规格里，不放进界面。

## 研究背景（只在规格里）

- METR 2025：16 个有经验的开源开发者，在自己熟悉的仓库做 246 个任务。用 AI 工具时完成时间长了约 19%，但他们自己估计快了约 20%。单个随机对照试验，样本小，用的是 2025 年初的工具。我没读到原文，来自二手报道。
- Brynjolfsson 等（NBER w31161）：5179 名客服用 AI 后每小时解决的问题多 14%，新手多 34%，老手几乎没变化。准实验，不是写代码。
- 两项结论相反，所以不替用户下结论，只给出可以对比的数字。

## 现有数据调查

| 想知道的 | 现有记录 | 够不够 |
| --- | --- | --- |
| 任务状态 | `coding_tasks.status`：queued、running、review、failed、canceled、committed、pushed、pr_opened、discarded | 够 |
| 仓库 | `coding_tasks.repo_id` 对应 `coding_repos.name` 和 `github_repo` | 够 |
| 工具 | `coding_tasks.executor`：claude 或 codex | 够 |
| Agent | `coding_tasks.ai_agent_id` 对应 `ai_agents.name`；手动建的任务为空 | 够 |
| 开始、结束 | `started_at` 是第一次开始，`finished_at` 是最后一次结束。任务被继续执行时，中间等待的时间也在两者之间 | 不能直接当运行时长 |
| 运行时长 | 只执行一次时 `finished_at - started_at` 就是运行时长。执行多次时，每次执行结束都会在 `ai_usage` 记一条 `duration_ms`（只有带用量的执行才有） | 一次执行够用。多次执行靠用量记录，可能缺 |
| 返工轮数 | 没有计数。每次执行（包括构建失败后自动重试、回答 Agent 的问题后继续）结束时，`coding_task_events` 写一条带退出码的 `done` 事件。构建结束也写 `done`，但没有退出码，要排除 | 执行次数减一 |
| 花费 | `ai_usage`，`source = 'coding'`，`ref` 是任务编号。Claude Code 带自己报的美元费用。Codex 不报费用，也没有价格表，`cost` 为空，但有 Token 数 | Claude 有，Codex 只有 Token |
| 是否产生 PR | `coding_tasks.pr_url` | 够 |
| PR 是否合并 | 编码任务没有记。GitHub 模块的缓存 `github_cache_v2`（种类 `pull`）只留打开的和最近 7 天关闭的。Git 回调（webhook）收到合并会发 `coding_task.merged` 事件，但不存 | 不够，要自己记 |
| 撤销时间 | 丢弃任务时 `updated_at` 就是丢弃时间（丢弃之后没有别的更新） | 够 |
| 审查时间 | 电脑时间 `screen_minutes`，每台电脑每分钟一行，有类别 `coding` | 能取 |

内置 Agent（`kind = builtin`）不走编码任务。它的运行记录只保留最近 200 条，用量的关联字段是 Agent 编号而不是运行编号，算不出每次运行的花费。所以这份对账只管 Claude Code 和 Codex 的编码任务，内置 Agent 不在里面。

## 怎么做

### 记下合并结果

新表 `codingroi_outcomes(task_id, outcome, at, source, pr_url)`，`outcome` 是 `merged` 或 `closed`。两个来源：

1. 订阅 `coding_task.merged` 事件，按事件里的任务编号记 `merged`，时间取收到时间，来源 `webhook`。
2. 每 30 分钟，以及每次打开报表时，查状态是 `pr_opened` 又没记过结果的任务，到 `github_cache_v2` 里按 PR 地址找。状态是 `merged` 或 `closed` 就记下，时间取缓存里的 `updatedAt`（合并或关闭时 PR 会更新），来源 `github`。

只读别的模块的表，不改它们的数据。读别的模块的表有先例（`aiagents` 读 `coding_tasks` 和 `ai_usage`），迁移只加不删，所以列不会消失。

### 一个任务的指标

任务按创建时间（服务器时区）归到某一周或某一月。

- 结果：
  - `merged`：已记合并。
  - `reverted`（被撤）：状态 `discarded`，或 PR 已关闭但没合并。
  - `canceled`：状态 `canceled`。
  - `failed`：状态 `failed`。
  - `waiting`（待合并）：`committed`、`pushed`、`pr_opened` 且还没有结果。
  - `active`（进行中）：`queued`、`running`、`review`。
- 执行次数：带退出码的 `done` 事件数。没有 `done` 事件但开始过又结束了的任务（服务重启时被中止）算一次。
- 运行时长：执行不超过一次时是 `finished_at - started_at`。执行多次时，这两个时间之间有等你的时间，所以改为把各次执行的 `ai_usage.duration_ms` 加起来，一条记录都没有就是无记录。没有开始过的任务不适用，也不算缺记录。
- 返工轮数：执行次数减一。没有执行过的是无记录。
- 花费：该任务所有用量记录的费用加起来。一条都没有，或所有记录的费用都为空，是无记录。部分记录为空时加已有的，并标“部分”。
- Token：输入和输出各自加起来。没有用量记录是无记录。
- 审查返工时间（估算）：见下节。
- 审查/运行：审查分钟除以运行分钟。两者都有、运行大于 0 才算。大于 1 表示看和改花的时间比 AI 跑的还长。

“花费/合并”在单个任务上没有意义，一个任务最多合并一次，比值就是它自己的花费。所以任务行给“审查/运行”，“每次合并”的比值只在分组和合计上算。

### 审查返工时间的估算

近似值，界面上写明是估算。

1. 每个任务一个审查窗口：从最后一次执行结束（`finished_at`）到结局。结局是合并或关闭的时间，或丢弃的时间（丢弃后任务没有别的更新，`updated_at` 就是丢弃时间）。
   - 失败和取消的任务没有窗口，审查时间不适用。
   - 还没有结局的任务（等你决定、已提交、已推送、已开 PR）算到现在，状态标“进行中”。
   - 窗口最长 72 小时，超过的部分不算。没有结局的老任务也受这个上限，不会越算越多。
   - 多次执行之间的空档不算。构建失败后自动重试几乎没有空档，回答 Agent 问题的等待要另外记，这一版不做。
2. 取这些窗口里电脑时间类别是 `coding` 的分钟数（所有电脑去重，同一分钟只算一次）。
3. 同一分钟落在几个任务的窗口里，平分给这几个任务，所以所有任务加起来不会超过实际的编码分钟。只在同一期（同一周或同一月）的任务之间平分。
4. 窗口里一分钟电脑时间记录都没有，就是无记录，不是 0 分钟。有记录但没有编码类，是 0。
5. 电脑时间模块被隐藏且已锁定时，全部按无记录算。

这个数里混着和这个任务无关的编码时间，只适合看趋势和比较，不是精确的审查时长。

### 汇总

分组方式三选一：`repo`（仓库）、`tool`（Claude Code、Codex）、`agent`（AI Agent 名称，没有 Agent 的是“手动任务”）。每组算：

- 任务数，合并、被撤、取消、失败、待合并、进行中各几个。
- 合并率 = 合并 / (合并 + 被撤 + 取消 + 失败)，没有已有结局的任务时无记录。
- 花费合计、有几个任务无花费记录。Token 合计同理。
- 运行时长合计、审查分钟合计、各自有几个任务无记录。
- 返工轮数合计。
- 每次合并的花费、运行分钟、审查分钟。没有合并时无记录。花费或运行或审查有缺的任务时，比值只用有记录的部分，界面在数字前写“至少”。

## 没有的数据

- Codex 不报美元费用，Token 能看但不能折成钱。报表里 Codex 任务的花费是无记录，只给 Token。要折成钱需要价格表，不在这一条里。
- 内置 Agent 的运行（见上）。
- 手动在终端里跑、不经过面板的 AI 工具（比如直接在 IDE 里问 Claude），没有任何记录。
- 合并只认两个来源：Git 回调和 GitHub 缓存。Forgejo 要配回调才知道合并。只提交、推送、没建 PR 的任务，合并没有记录，一直是“待合并”。直接在命令行合并的也一样。
- 审查时间只来自电脑时间，且只有 Windows 代理上报的分钟。手机或没装代理的电脑上的审查看不到。
- 在这一条上线之前已经合并的 PR，除非还在 GitHub 缓存的 7 天内，否则都是“待合并”。

## 接口

`api/modules/codingroi.yaml`：

- `GET /codingroi/report?period=week|month&date=YYYY-MM-DD&groupBy=repo|tool|agent`：返回 `{period, from, to, groupBy, screenAvailable, totals, groups, tasks}`。`date` 是期内任意一天，默认今天；周从周一开始。
- `GET /codingroi/report.csv`：同样的参数，导出任务明细 CSV（UTF-8 带 BOM）。无记录的格子为空。

动作目录：`codingroi.weekly`（读）。输入 `date`（可选）、`groupBy`（可选）。返回那一周的合计和分组，任务只带前 30 个。

## 界面

路径 `/coding/roi`，左栏“Agent”的二级菜单里加一项“投入产出”。不新开一级入口。

- 页面按 `docs/07-design.md`：`StatStrip` 概要卡片，`Toolbar`，主体，加载、空、出错、还没上线、手机五种状态。
- 页面顶部一句说明，另一句写明审查时间是估算。
- Toolbar：周/月切换、上一期和下一期、日期显示、按仓库/按工具/按 Agent 切换、导出 CSV。
- 概要卡片：任务数、合并（和合并率）、花费、AI 运行时长、审查时间（估算）。
- 分组表：每组一行，可按列排序。
- 任务明细表：可按列排序，标题点进任务页。
- 没有记录的格子显示“无记录”。手机上表格在容器里横向滚动，整页不滚动。

## 默认做法

- 周从周一开始，用服务器时区，和电脑时间模块一致。
- 任务归期按创建时间，不按结束时间。上周创建、这周合并的任务算上周。
- 审查窗口上限 72 小时，写成常量，不放设置。
- 只统计 `coding` 类别，不含 `ai` 类别（Claude、ChatGPT 桌面程序）。审查多半在编辑器和终端里。
- 不做缓存表，每次打开实时算。一期最多几百个任务，电脑时间最多几万行，够快。
- 不加设置开关，报表不向外发送任何数据。
- 隐藏模块：“Agent”整块被隐藏并锁定时，接口和动作都不可用（和 `aiconfig` 一样归到 `coding`）。只隐藏“时间去向”时，报表还能看，但审查时间全是无记录。
- 只读别的模块的表，不新加合约。新加的共享改动只有 `contracts/hidden.go` 的两处映射。
- 被撤数把“丢弃”和“PR 关闭未合并”合在一起。取消（任务跑到一半手动停止）单独列。

## 验收标准

1. 一周里有多个仓库、Claude 和 Codex 任务时，三种分组的数字都对，总计等于各组之和。
2. 缺数据的格子是无记录，不是 0；比值遇到缺数据按规则处理。
3. 审查时间：窗口、72 小时上限、同一分钟平分、无记录和 0 的区别都有测试。
4. 合并结果能从事件和 GitHub 缓存两处记下，重复记不出错。
5. CSV 能直接用 Excel 打开，有表头，公式前缀被转义。
6. 页面：周切换、分组切换、排序、导出、空和出错状态有测试。
7. `codingroi.weekly` 动作至少跑一次。

## 没有验证的

- 没有连真实的 Claude Code、Codex 和 GitHub。用量、事件、PR 状态都是测试里直接写进数据库的，格式照现有代码里的写入方式。
- 没有在真实的 Windows 代理上采集电脑时间，分钟数据也是测试里写入的。
- 没有跑截图和端到端，交给 CI。
