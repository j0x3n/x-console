# B47 Agent 管理：建 Agent、连 GitHub 和 Forgejo、在选定的机器上改代码和编译

用户 2026-09-30 提出：左栏加“Agent 管理”，可以创建、管理 Agent。Agent 能连 GitHub 或自己部署的 Git 服务（比如 Forgejo）修改代码，并且能在选定的服务器或 Windows 电脑上跑编译。运行位置让审查者定。

## 现状

- “Agent 任务”（`coding` 模块）已经能在一台电脑上用 Claude Code 或 Codex CLI 改代码：建 worktree 和分支、跑执行器、看改动、提交、推送、开 GitHub PR。
- 限制：只有 Windows 代理有 `coding` 能力，Linux 服务器不能跑；仓库要先手动放到那台机器上，按本地路径登记；只支持 GitHub 开 PR；没有“Agent”这个概念，每次任务临时选执行器和提示词；没有编译这一步。
- 数据库里已有 `agents` 表，存的是已配对的代理程序（服务器和电脑）。新概念不能再叫这个表名，见下面的命名。

## 运行位置：在代理所在的机器上跑，不在 X Console 服务端里跑

理由：

1. 服务端镜像里没有 Go、Node、.NET 这些编译工具，也不应该装。各个项目要的工具链不一样，放在各自的机器上配。
2. 让 AI 执行命令、跑别人仓库里的构建脚本，风险在执行它的那台机器上。放在服务端进程里跑，出问题会影响整个控制台和数据库。
3. Windows 程序要在 Windows 上编译，只能放到 Windows 电脑上跑。
4. 代理协议已经有 `coding.run` 这一套，只要给 Linux 代理也加上 `coding` 能力。
5. 想“在服务器上跑”的，服务端那台机器本身装了本机代理（B1），选它就行。

以后要更强的隔离，再加“在 Docker 容器里跑”的选项（见最后“以后再做”）。

## 命名

- 界面上叫“Agent”。左栏原来的“Agent 任务”改成“Agent”，点进去是 Agent 管理页，原来的任务列表变成里面的一个页签。
- 代码里新模块叫 `aiagents`，表名前缀 `ai_agent`。不要用 `agents`，那是代理程序。
- 本规格里“代理”指装在机器上的代理程序，“Agent”指这次新加的 AI Agent。

## 1. Agent

新表 `ai_agents`：

| 字段 | 说明 |
| --- | --- |
| `name`、`avatar`（emoji）、`color` | 在卡片成员里显示 |
| `kind` | `claude_code`、`codex`：在代理机器上跑 CLI，适合改代码。`builtin`：用 X Console 自己的 AI 供应商（B32）加动作注册表里的工具，适合整理卡片、写笔记、做总结，不碰代码 |
| `model` | `builtin` 必填，选 B32 的模型。CLI 可选，填了就用 `--model` 传给执行器 |
| `instructions` | Agent 的固定说明，每次任务都放在提示词最前面。比如“你是后端开发，只改 backend 目录，提交前跑 go test” |
| `runner_agent_id` | 默认在哪台机器上跑（代理 id）。只能选有 `coding` 能力的 |
| `access` | `builtin` 用：和 B43 令牌一样三级，`read`、`write`、`write_delete`。`dangerous` 的动作永远不给 |
| `cli_permission` | CLI 用：`workspace`（只能改工作目录，默认）或 `full`。对应 Codex 的 `--sandbox workspace-write` / `danger-full-access`，Claude Code 的 `--permission-mode acceptEdits` / `bypassPermissions`。选 `full` 要提升权限 |
| `repo_ids` | 允许操作的仓库，空表示不能碰代码 |
| `max_parallel` | 同时跑几个任务，默认 1 |
| `monthly_budget_usd` | 本月费用上限（按 B42 的用量算），到了以后不接新任务，已经在跑的不打断。空表示不限 |
| `enabled` | 停用后不接新任务 |

Agent 管理页：Agent 列表（头像、名字、类型、默认机器、本月费用、正在跑的任务数），新建和编辑表单，每个 Agent 的详情页显示它的任务历史和用量。

## 2. Git 连接

新表 `git_connections(id, kind, name, base_url, username, token_enc, created_at, last_checked_at, last_error)`：

- `kind`：`github`、`forgejo`、`gitea`。Forgejo 和 Gitea 的接口一样（`/api/v1`），代码里当一种处理。
- `base_url`：GitHub 固定 `https://api.github.com`；Forgejo 填自己的地址，比如 `https://git.example.com`。
- 令牌用 `secrets.Box` 加密存，接口永远不返回明文。新建、改令牌、删除要 `auth.RequireElevated`。
- GitHub 可以选“用 GitHub 模块已有的令牌”，不用再填一遍。
- 保存时检查一次：GitHub 调 `GET /user`，Forgejo 调 `GET /api/v1/user`，把用户名存下来，失败时存 `last_error`。
- 需要的令牌权限写在表单说明里：GitHub 细粒度令牌要 Contents 读写、Pull requests 读写；Forgejo 要 `write:repository`。

## 3. 仓库改成按远端登记

- `coding_repos` 加列（只加不删）：`connection_id`、`owner`、`repo`、`clone_url`、`build_config`。
- 新登记方式：选 Git 连接，从它能访问的仓库里搜索选择（GitHub `GET /user/repos`，Forgejo `GET /api/v1/user/repos`），再选运行机器。本地路径自动定为代理工作目录下的 `repos/<连接id>/<owner>/<repo>`。
- 原来按本地路径登记的方式保留，`connection_id` 为空。
- 新协议方法 `coding.ensure_repo`：代理检查目录，没有就 `git clone`，有就 `git fetch`。写进 `docs/04-agent-protocol.md`。
- 凭据：服务端只在需要的那一次调用（`ensure_repo`、`push`）里把令牌发给代理。代理用 `git -c http.extraHeader=...` 或临时的 `GIT_ASKPASS` 传令牌，不写进 `.git/config`，不写磁盘，输出里出现令牌时替换成 `***`。
- 开 PR：GitHub 走已有的逻辑；Forgejo 调 `POST /api/v1/repos/{owner}/{repo}/pulls`。PR 地址存进任务，同时加到卡片的关联里。
- Linux 代理加 `coding` 能力：执行器检测、worktree、`coding.run` 这一套在 Linux 上也能用。`docs/04-agent-protocol.md` 能力表里 `coding` 改成 Linux 和 Windows 都有。

## 4. 编译

- 仓库设置里加“构建步骤”（存 `build_config`，JSON）：每步有名字、命令、超时、产物路径（glob，可选）。可以按系统分开写（Linux 一套，Windows 一套），跑的时候按机器的系统选。
  - 例子：`go test ./...`、`npm ci && npm run build`、`dotnet publish -c Release`。
- 新协议方法 `coding.build`（流式，和 `coding.run` 一样的事件格式）：在任务的 worktree 里按顺序执行构建步骤，一步失败就停。
- 什么时候跑：
  - Agent 改完代码以后自动跑一次（Agent 设置里可以关）。
  - 失败时可以自动把错误日志的最后 200 行交给同一个 Agent 再改一次，最多重试次数在 Agent 设置里填，默认 2。
  - 任务详情里手动点“构建”。
  - 不经过 Agent，直接对某个分支跑一次构建（“只编译”任务）。
- 产物：构建成功后，代理把产物路径匹配到的文件上传到云盘 `files/agents/<任务id>/`，走 `files.Store`。单个文件最大 2 GB，总共最多 50 个文件。任务详情里列出来，可以下载。
- 构建日志存进 `coding_task_events`，任务详情里按步骤折叠显示，用 B31 的日志查看方式。

## 5. 和项目看板（B46）配合

- 卡片的“分配给 Agent”：选 Agent，确认框里显示仓库、基础分支、运行机器（默认用 Agent 的设置，可以改）。确认后：
  - 建一个 Agent 任务，提示词是：Agent 的固定说明 + 卡片标题、描述、未完成的清单条目、最近 10 条评论。`issue_key` 写卡片编号。
  - Agent 加进卡片成员，卡片移到状态为“进行中”的列表。
  - Agent 开始、构建结果、结束时各在卡片上写一条评论（actor 是 `agent:<id>`），结束的评论里有改动的文件数和 PR 链接。
  - 结束后卡片移到状态为“审查中”的列表。失败时卡片不动，评论里写失败原因，卡片上的 Agent 头像显示红点。
- `builtin` 类型的 Agent 被分配卡片时，不开 worktree，直接用动作注册表干活（比如“把这张卡拆成子任务清单”），结果写成评论或清单。
- 多个 Agent 同时干活：每个 Agent 按 `max_parallel` 排队，每台机器按原来的“最大并发数”排队。看板上能看到哪些卡片正在被哪个 Agent 处理。
- Git 服务的回调：新接口 `POST /api/v1/hooks/git/{connectionId}`，公开入口，必须校验签名（GitHub `X-Hub-Signature-256`，Forgejo `X-Forgejo-Signature`，密钥在连接里生成，加密存）。PR 合并时，对应卡片移到“已完成”，任务状态改成已合并。

## 6. 安全

- 创建和修改 Git 连接、把 Agent 的 CLI 权限改成 `full`、修改 Agent 能访问的仓库，都要 `auth.RequireElevated`，写审计日志。
- Agent 只能推送到自己建的分支（`xc/<任务id>-<简短名>`），不能推送默认分支，不能强推。代理在 `coding.push` 里检查分支名。
- `builtin` Agent 调动作的规则和 B43 令牌完全一样，复用同一个过滤函数。
- 执行器和构建命令只在 worktree 目录里运行，环境变量里不带服务端的任何密钥。

- Agent 的增删改、停用、预算到了不接新任务，都有测试。
