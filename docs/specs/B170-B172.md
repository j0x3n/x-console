## B171：匹配时写入专辑，批量补全专辑（后端 Codex，按钮 Claude）

现状：`matcher.go` 的 `applyFound` 只存歌词和封面，不存候选里的 `Album`。所以匹配到封面的歌专辑仍是空，专辑视图全是“未知专辑”。

### 匹配时写入

- 匹配（后台自动匹配、用户在待确认里选候选）应用结果时，如果这首歌的 `album` 为空、`manual` 为 0，而采用的候选 `Album` 不为空，就写入 `album`。
- 候选有 `Album` 才写。专辑已经有值的歌不改。
- 打开“写回文件”时，专辑一起写进文件标签（`writeback.go` 的 `writeBack` 加 `album` 参数，其余行为不变）。写回后更新 sha，和现有歌词、封面一致。
- 只改专辑，不改 `title`、`artist`、`album_artist`。

### 批量补全专辑

- 新接口 `POST /music/fill-albums`，operationId `fillMusicAlbums`，返回 `202 { total: number }`。已经在跑时返回 `409`。没有可处理的歌时 `total` 为 0，不开后台任务。
- 处理对象：`album = ''` 且 `manual = 0` 且 `match_state != 'skipped'` 的歌。
- 对每首歌用现有的来源搜索（`search`），只取候选的 `Album`，选第一个通过 `accepts(q, c)` 且 `Album` 不为空的候选。不抓歌词和封面，不改 `match_state`，不留候选。
- 找不到就跳过，不标失败，下次点还会再试。每个来源的请求间隔沿用现有限速。
- 进度事件 `music.album_progress`，数据 `{ running: bool, done: int, total: int, current?: string }`，和 `music.match_progress` 同形。结束时再发 `music.library_changed`。
- 同一时间只允许一个补全任务，和 `runMatches` 的匹配任务互斥（匹配在跑时返回 `409`）。

### 验收

- 单元测试：匹配到带专辑的候选后，空专辑被写入；已有专辑不被改；`manual = 1` 不被改；写回开关打开时文件标签里有专辑。
- 集成测试：`fill-albums` 用假来源，只补专辑为空的歌，进度事件和 `409` 行为正确。
- `api/modules/music.yaml` 加新接口和事件说明，`go generate ./...` 的结果提交。

## B172：来源请求走 Windows 代理网络（后端 Codex，来源显示 Claude）

用户 2026-10-13 定的做法：服务端直连来源失败时，自动改走一台在线的 Windows 代理发请求。

### 代理新命令

- 新能力 `net.fetch`，Linux 和 Windows 代理都实现（命令在 `backend/pkg/protocol/`，处理在 `backend/internal/agent/`）。服务端只会选 Windows 代理，Linux 代理有这个命令是为了以后用，实现不要分平台。
- 方法 `net.fetch`，参数 `{ url, headers?, maxBytes?, timeoutMs? }`。
  - `url` 只接受 `https`，主机名必须在白名单里：`music.163.com`、`c.y.qq.com`、`u.y.qq.com`、`y.qq.com`、`y.gtimg.cn`、`lrclib.net`、`itunes.apple.com`、`musicbrainz.org`、`coverartarchive.org`，以及后缀为 `.mzstatic.com`、`.music.126.net`、`.gtimg.cn`、`.archive.org` 的主机。白名单放在 `protocol` 包里的一个常量，服务端和代理共用。
  - 只发 GET。`headers` 只接受 `User-Agent`、`Referer`、`Accept`、`Cookie`。
  - `maxBytes` 默认和上限都是 8 MiB，`timeoutMs` 默认 8000、上限 15000。
  - 跟随重定向，但每一跳的主机都要在白名单里，最多 5 跳。解析出的 IP 是私有、回环或链路本地地址时拒绝。
  - 返回 `{ status, contentType, body }`，`body` 是 base64。非 200 也照实返回，由服务端判断。
- 代理 hello 里上报能力 `net.fetch`。`docs/04-agent-protocol.md` 的能力表和命令列表同步更新。

### 服务端

- `providerSet.do`（`providers.go`）先直连。以下情况改走代理：网络错误（含超时）、HTTP 403、451、429、5xx、返回内容不是预期格式（`errSourceFormat`）。404 不改走。
- 代理选择：在线、有 `net.fetch`、系统是 Windows 的代理。有多台时取最近一次心跳最新的那台。没有可用代理就直接返回直连的错误，行为和现在一样。
- 同一个来源直连失败并且代理成功后，10 分钟内这个来源直接走代理，不再先试直连。代理也失败时不记，下次还是先直连。
- 封面下载（`FetchCover`）也走同一个入口。
- “检查来源”（`match_api.go` 里现有的来源检查）的结果每个来源加字段 `via`：`direct` 或 `agent`，走代理时再给 `agentName`。检查来源时先测直连，失败再测代理，两个结果都要能看出来。
- 不加设置项。想关掉代理的话以后再加。

### 验收

- 协议测试：白名单外的主机、`http`、私有 IP、重定向到白名单外、超过 `maxBytes` 都被拒绝。
- 服务端测试：用假代理（`testutil` 里现有的假代理连接）验证直连失败时走代理、404 不走、10 分钟内直接走代理、没有 Windows 代理时错误不变。
- `api/modules/music.yaml` 里来源检查的返回加 `via` 和 `agentName`，`go generate ./...` 的结果提交，Windows 代理 `GOOS=windows go build ./cmd/agent` 和 `go vet` 通过。
- 上线后要在真机上验：服务端连不上 QQ 音乐时，匹配能拿到歌词。这一项记进“已知问题”，因为开发环境没有真实的受限网络。

## B174：匹配补全所有歌曲信息，不只专辑（后端 Codex，文案 Claude）

2026-10-13 用户提的：歌手也没有匹配到，要把匹配改成所有歌曲信息都补完整。

原因：`accepts` 要求歌手有重叠（`artistsOverlap`）。歌曲自己没有歌手时一定不通过，所以这类歌永远进“待确认”，歌手也没人写进去。

### 要补的字段

歌手 `artist`、专辑 `album`、专辑歌手 `album_artist`（只有来源明确给出才补，iTunes 的 `collectionArtistName`）、年份 `year`（来源有发行日期才补，只取年份）。标题、曲目号、碟号不补。

候选 `candidate` 加 `Year int` 和 `AlbumArtist string`，各来源从返回里取：网易云 `publishTime`、QQ 音乐 `publictime`、iTunes `releaseDate` 和 `collectionArtistName`、MusicBrainz `date`。LRCLIB 没有就留空。

### 规则

- 只填空的字段：`artist` 为空、`album` 为空、`album_artist` 为空、`year` 为 0。有值的不改。`manual = 1` 的歌不动。
- 歌手为空的歌：用标题和时长做更严的自动采用，也就是标题完全一致（`titlesMatch`）且时长差不超过 2 秒，满足才采用，并把候选的歌手填进去。没有时长的歌（`DurationMs` 为 0）不自动采用，进待确认。
- 搜索时歌手为空，查询里不带歌手。检查各来源的 `Search` 在歌手为空时能正常搜（不要拼出多余空格或空参数）。
- 歌手填进去以后，再用这个歌手判断其他候选（歌词、封面）是否匹配，顺序是先定歌手再抓歌词封面。
- 用户在待确认里选候选（`applyCandidate`）时，同样补空字段，歌手为空时也填。
- 开了“写回文件”时，补到的歌手、专辑、年份一起写进标签，读回校验和现有方式一致。

### 批量补全

沿用 B171 的接口和事件，**名字不改**：`POST /music/fill-albums`、`music.album_progress`。行为扩大成“补全信息”：

- 处理对象改为 `manual = 0` 且 `match_state != 'skipped'` 且 `artist`、`album`、`year`（为 0）任意一项为空的歌。
- 只查信息，不抓歌词和封面，不改 `match_state`，不留候选。
- `api/modules/music.yaml` 里这个接口和事件的描述改成“补全歌手、专辑、年份等信息”，字段和返回不变。
- 后台自动匹配（`matchTrackParts`）找到结果时也补这些字段，不只在专辑为空时。

### 验收

- 歌手为空的歌：标题一致且时长相差不超过 2 秒的候选被自动采用，歌手被写入。时长缺失、标题只是部分一致的不自动采用。
- 有歌手的歌行为不变。已有值的字段不被改，`manual = 1` 不被改。
- 年份只在有值时写，且 0 或负数不写。
- 批量补全：只补空字段，只处理上面列的歌，进度事件和 `409` 行为不变。
- 开写回时标签里有歌手、专辑、年份。
- `check-quick.sh` 通过，Windows 代理交叉编译通过，`go generate` 的结果提交。
