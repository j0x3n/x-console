# B71 仓库事件通知

## 后端实现差异（2026-10-02）

- 通知设置、13 种事件、账号隔离和仓库覆盖已实现。每种资源都有持久的初始化标记，首次成功同步即使为空也静默。请求失败保留上次状态，通知入库失败会一起撤回比较状态和去重记录。
- CI 事件以运行编号和重试次数识别。默认只通知默认分支；选 all 后包含其他分支和 PR 运行。PR 检查汇总继续展示，通知按运行事件发送，避免和 CI 运行重复。
- 新增同步调用的 `contracts.GitWebhookReceiver`。aiagents 校验签名后调用，失败返回错误供上游重试。原来的 PR 合并卡片流程保留。原始回调正文只传给服务契约，不向浏览器事件总线发布。
- 回调 delivery 编号和语义事件均持久保存一天。语义键包含账号、仓库、事件、对象和状态。push 按每个 SHA 去重后合成一条；运行包含 attempt，release 使用 tag。评审回调先取最新评审汇总，保持和同步结果一致。
- 每个账号、仓库、事件一分钟最多三条详细通知。多出的数量持久保存，由每分钟独立任务或下一次事件发一条“还有 N 条”，重启后继续处理。通知、限流窗口、比较状态和去重记录同事务提交。外部渠道沿用现有提交后异步发送；进程在提交后发送前退出时，通知中心记录保留，外部渠道没有自动补发保证。
- Forgejo release 使用带 ETag 的列表接口并排除 draft 和 prerelease。Actions 能力及旧版本提交状态降级遵循 B70 的探测结果；服务器未提供 workflow_run 回调时由同步发现变化。真实 Forgejo 实例尚未验证，能力组合已用假服务覆盖。


用户 2026-10-01 提的：关注的仓库，重要的操作和更新都要能设置通知，比如 CI 开始、成功、失败，有新的提交、新的 PR 等等。

现在只有默认分支 CI 失败会发一条 `github.ci_failed`。

## 事件

| 键 | 什么时候发 | 默认 |
| --- | --- | --- |
| `ci_started` | 一条运行从排队变成进行中 | 关 |
| `ci_succeeded` | 运行成功 | 关 |
| `ci_failed` | 运行失败或超时 | 开 |
| `ci_cancelled` | 运行被取消 | 关 |
| `ci_recovered` | 默认分支上一次失败、这一次成功 | 开 |
| `push` | 有新的提交（只看默认分支） | 关 |
| `pr_opened` | 有人开了 PR | 开 |
| `pr_merged` | PR 合并了 | 开 |
| `pr_closed` | PR 没合并就关了 | 关 |
| `pr_review` | PR 有了评审结果（通过或要求修改） | 开 |
| `issue_opened` | 有新的 Issue | 关 |
| `issue_assigned` | Issue 指派给了我 | 开 |
| `release` | 发布了新版本 | 开 |

CI 的几个事件另有一个范围：`ciBranches` 取 `default`（只看默认分支，默认值）或 `all`（所有分支和 PR）。

## 界面

- **设置 → Git 与仓库 → 通知**：一张卡片，列出上面的事件，每个一个勾选框，分“CI”“提交”“PR”“Issue 和发布”四组。下面一个下拉框选 CI 范围。这是所有仓库的默认设置。
- **仓库页**：选了某个仓库时，标题行有一个铃铛按钮。点开弹窗：上面“跟随默认设置”开关，关掉后可以单独勾选这个仓库的事件。铃铛上有一个小点表示这个仓库单独设置过；全部关掉时铃铛画斜线。
- 通知走现有的通知中心，渠道（浏览器推送、Bark、Telegram）照“设置 → 通知”里的规则。通知的种类是 `github.<事件键>`，比如 `github.ci_failed`，可以在通知设置里按种类单独路由。
- 通知内容：标题“x-console · CI 失败”，正文“CI · main · 修复登录（a1b2c3d）”，点击跳到仓库页对应的标签（`/github?repo=...&tab=runs`）。

## 契约（`api/modules/github.yaml`，已改）

- 新接口 `GET /github/notify`、`PUT /github/notify`：`GitHubNotifySettings = { defaults: RepoNotify, repos: RepoNotifyOverride[] }`。
  - `RepoNotify = { events: string[], ciBranches: "default" | "all" }`，`events` 是上表里开着的键。
  - `RepoNotifyOverride = { connectionId, repo, notify: RepoNotify }`。不在 `repos` 里的仓库跟随默认设置。
- `WatchedRepo` 加 `notifyCustom`（布尔，单独设置过）、`notifyOff`（布尔，单独设置成全部关闭）。

## 后端（待做）

1. 设置键 `github.notify`，JSON。没有时用上表的默认值。旧的 `github.ci_failed` 通知改成走这里（`ci_failed` 默认开，行为不变）。
2. 发现事件：同步时和上一次的缓存比较。
   - CI：运行的 `status` 或 `conclusion` 变了。第一次同步（缓存是空的）不发，免得一下子来一堆。
   - push：默认分支最新提交的 sha 变了。一次同步里多个新提交合成一条：“3 个新提交，最新：修复登录”。
   - PR：新出现的打开的 PR、状态变成 merged 或 closed、`reviewState` 变成 approved 或 changes_requested。
   - Issue：新出现的打开的 Issue；指派人里新出现了自己（`login`）。
   - release：同步时拉最新一个 release（GitHub `GET /repos/{o}/{r}/releases/latest`，带 ETag；Forgejo `/repos/{o}/{r}/releases?limit=1`），tag 变了就发。
3. 有 Git 回调（B47 的 `/hooks/git/{connectionId}`）时，收到 `workflow_run`、`push`、`pull_request`、`issues`、`release` 事件直接发通知，并记下事件编号，同步时不再重复发同一件事（按“仓库 + 事件键 + 对象编号 + 状态”去重，记 1 天）。
4. 同一个仓库 1 分钟内同一个事件键最多发 3 条，多了合成一条“还有 N 条”。
5. 测试：假 GitHub 服务里改运行状态、加提交、开关 PR，检查发出的通知种类和条数；第一次同步不发；单独设置覆盖默认设置；回调和同步不重复。

## 验收

- 默认设置下，默认分支 CI 失败、开新 PR 会收到通知；CI 开始不会。
- 给某个仓库单独勾上“CI 开始”，推一个提交后收到“CI 开始”。
- 仓库页铃铛显示这个仓库是不是单独设置过。
