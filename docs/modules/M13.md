# M13 开发者集成：GitHub 与 Linear

负责批次：2（任务卡 H）。两个后端模块：`modules/github` 和 `modules/linear`。前端都在 `features/github`。

## GitHub

### 设置

| 键 | 说明 |
| --- | --- |
| `github.token` | 细粒度 PAT，加密保存，接口只返回打码后的样子 |
| `github.repos` | 关注的仓库，`owner/name` 列表，最多 50 个。也接受 `https://github.com/owner/name` |
| `github.api_url` | REST 地址，默认 `https://api.github.com`。测试和 GitHub Enterprise 用 |
| `github.login` | 令牌对应的用户名，同步时自动更新 |
| `github.last_sync` | 最近一次同步的时间和错误 |

改令牌、删除令牌或改 API 地址需要提升权限；只改仓库列表不需要。

### 同步

- 用 REST API，直接 `net/http`，不引入 go-github。每 5 分钟一次（调度器 `github.sync`），也可以 `POST /github/sync` 手动触发。
- 每个仓库：`GET /repos/{repo}`（默认分支）、打开的 PR（`per_page=100`，只取第一页）、每个 PR 的评审和 head 提交的检查（commit status + check runs 合并）、最近 20 次 workflow run、分配给你的和你创建的打开的 Issue（各取 50 条，去掉 PR）。
- 评审状态：每个评审人最后一次有效评审。有人要求修改 → `changes_requested`；有人批准 → `approved`；请了评审没人评 → `pending`；只有评论 → `commented`；否则 `none`。
- 检查状态：有失败（failure、timed_out、action_required、startup_failure）→ `failure`；有没结束的 → `pending`；都成功（含 neutral、skipped）→ `success`；没有检查 → `none`。cancelled 不计入。
- 读取 CI 或 Issue 没有权限时，这一部分的错误记在同步结果里，PR 照常同步。仓库关掉 Actions（404）时清空它的运行记录。
- 取消关注的仓库，缓存会在下次同步时删掉。关掉的 PR 从缓存删除。
- 条件请求：GET 响应带 ETag 的都缓存在内存里，下次带 `If-None-Match`，304 时用缓存的内容（不占限额）。
- 限流：记下 `X-RateLimit-Remaining` 和 `X-RateLimit-Reset`。返回 403/429 且剩余为 0 或带 `Retry-After` 时，到重置时间前不再发请求，同步结果里写明原因。

### 缓存表

`github_pulls`、`github_runs`、`github_issues`、`github_links`（PR 和本地 Issue、编码任务的关联）、`github_ci_states`（每个 PR 和每个默认分支 workflow 最近一次确定的结果）。

### CI 通知

- kind `github.ci_failed`，优先级 high，链接 `/github` 或 `/github?tab=runs`。
- PR：检查结果从 success 变成 failure 时发一次。中间的 pending 不算，所以 success → pending → failure 也只发一次；一直是 failure 不再发；变回 success 再变 failure 会再发。第一次看到就是 failure 的不发。
- 默认分支：每个 workflow 最近一次结束的运行，从 success 变成 failure 时发一次。cancelled、skipped 不算。

### 关联

- PR 标题或分支名里出现 Issue key（不分大小写，如 `XC-12`、`feature/xc-12-login`）且本地有这个 Issue 时，调用 `contracts.Issues.AttachLink`（kind `pull_request`，ref `owner/name#34`）。每个 PR 和 Issue 只关联一次，记在 `github_links`，避免每 5 分钟重复写审计日志。
- 分支是 `xc/<任务id>-...` 时只记录 `coding_task` 关联，接口里返回 `codingTaskId`，不依赖 M4。

### 接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET/PUT | `/github/config` | 配置。PUT 的 `token` 留空表示不改，`clearToken: true` 删除 |
| POST | `/github/test` | 用令牌读 `/user`。不带请求体测已保存的；带请求体测表单里的值，需要提升权限 |
| GET | `/github/status` | 是否配置、是否在同步、上次同步时间和错误、剩余请求数 |
| POST | `/github/sync` | 立即同步，结束后返回状态 |
| GET | `/github/pulls?repo=` | 打开的 PR，带 `issueKeys`、`codingTaskId` |
| GET | `/github/runs?repo=&limit=` | 最近的运行，带 `defaultBranch` |
| GET | `/github/issues` | 分配给你或你创建的 Issue，带 `relation` |

未配置令牌时列表和同步返回 412 `integration_not_configured`。同步结束发事件 `github.synced`，建 PR 发 `github.pull_created`。

### contracts.GitHub 和动作

- `CreatePR` 调 `POST /repos/{repo}/pulls`，写审计 `github.create_pr`。仓库在关注列表里时马上放进缓存，并做 Issue 关联。GitHub 拒绝时返回 502 `github_error`，信息里带原因。
- 动作：`github.list_pulls`（read，可按 repo 过滤），`github.create_pr`（write）。

### 令牌权限

细粒度令牌，只选关注的仓库。只读：Pull requests、Issues、Actions、Commit statuses、Metadata。要建 PR 时 Pull requests 给读写。

## Linear 同步

### 设置

| 键 / 表 | 说明 |
| --- | --- |
| `linear.api_key` | 个人 API key，加密保存，打码返回 |
| `linear.api_url` | GraphQL 地址，默认 `https://api.linear.app/graphql` |
| `linear.last_sync` | 最近一次同步结果 |
| `linear.local_cursor` | 上次成功同步的开始时间，用来找本地改过的 Issue |
| `linear_teams` 表 | 团队 ↔ 本地项目，一对一；`cursor` 是已经拉到的 Linear 最新 `updatedAt` |
| `linear_issues` 表 | 每个 Issue 上次同步时两边的更新时间 |

改 key、删除 key 或改地址需要提升权限；只改对应关系不需要。对应关系不变时保留拉取进度。

### 同步规则

- 字段：标题、描述、状态、优先级（0-4 两边一致）、截止日期（按用户时区的日期）。
- 状态：backlog、triage → backlog；unstarted → todo；started → in_progress，名字里带 “review” 的 started 状态 → in_review；completed → done；canceled → canceled。推到 Linear 时选同类型里位置最靠前的状态，in_review 优先选带 “review” 的，in_progress 避开它。团队没有 review 状态时，本地 in_review 和 in_progress 都算和 started 一致，不来回改。
- 判断谁改了：`linear_issues` 记着上次同步时两边的更新时间。只有 Linear 变了 → 写本地；只有本地变了 → 推 Linear；两边都变了 → `updatedAt` 较新的一方为准，记为冲突并写日志。内容已经一样时只更新记录。
- 本地只通过 `contracts.IssueSync` 读写：`FindByExternal`、`Upsert`（保留 Linear 的 `updatedAt`）、`ChangedSince`。本地 `external_source = 'linear'`，`external_id` 是 Linear issue id。
- 新建：Linear 里新出现、还没完成或取消的 Issue 建到对应项目里。已完成、已取消的不导入。本地新建的 Issue 不会建到 Linear。
- 触发：每 5 分钟（调度器 `linear.sync`）拉一次，按团队 `updatedAt > cursor` 取；也可以 `POST /linear/sync`。本地 `issue.created`、`issue.updated`、`issue.status_changed` 事件会马上推送有 Linear id 的 Issue。`Upsert` 发的是 `issue.synced`，推送忽略它，所以拉回来的改动不会再推回去。
- 推送失败（比如 Linear 连不上）时记到最近结果里，下次定时同步会用 `ChangedSince` 找到这些本地改动再推。
- 拉取时某条 Issue 出错，游标停在它前面，下次重试。

### 接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET/PUT | `/linear/config` | key（打码）、地址、对应关系 |
| POST | `/linear/test` | 读当前用户。带请求体时需要提升权限 |
| GET | `/linear/teams` | Linear 里的团队，配置对应关系时用。未配置时 412 |
| POST | `/linear/sync` | 立即同步，返回状态 |
| GET | `/linear/status` | 是否配置、对应组数、最近一次结果（导入、拉取、推送、冲突数和错误） |

同步结束发事件 `linear.synced`。

## 前端

- `features/github`：`/github` 页面三个标签：PR（按仓库分组，检查失败的排前面，带检查、评审、草稿、关联 Issue 和编码任务的标签）、CI 运行（默认分支每个 workflow 的最新结果 + 最近运行表格）、Issue（按仓库分组）。`?tab=runs` 直接打开 CI 运行。
- 设置页 “GitHub” 标签：令牌、仓库（一行一个）、API 地址、测试、保存后自动同步一次、同步状态和剩余请求数。
- 设置页 “Linear” 标签：API key、地址、团队 ↔ 项目的对应行、测试、同步状态（导入、拉取、推送、冲突、错误列表）。
- 命令面板：打开 GitHub、查看 CI 运行、GitHub 设置、Linear 同步设置。

## 验收

- 用 httptest 模拟 GitHub 和 Linear API（`github/fakegithub_test.go`、`linear/fakelinear_test.go`）。
- GitHub：同步后 PR、运行、Issue 正确；ETag 生效；关掉的 PR 和取消关注的仓库会清掉；CI 变红只通知一次，变绿再变红再通知；带 `XC-12` 的 PR 出现在 Issue 的关联里且只写一次；`xc/42-...` 对应编码任务；CreatePR 和两个动作；限流后暂停请求。
- Linear：拉取新建和更新本地 Issue；本地改状态、标题、优先级推到 Linear；两边都改时以较新的为准（两个方向各一例）；没有回声；推送失败后由定时同步补推。
